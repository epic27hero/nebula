1. Project Overview

What is Project Nebula?

Project Nebula is a complete, production-ready Kubernetes infrastructure designed to deploy, manage, and monitor containerized applications. It combines several powerful technologies to create an enterprise-grade platform that can scale applications reliably with minimal downtime.

Core Features:
✅ Containerized FastAPI Application with automatic scaling
✅ Kubernetes Cluster for container orchestration
✅ Continuous Delivery via ArgoCD (GitOps)
✅ Load Balancing with MetalLB
✅ Monitoring with Prometheus + Grafana
✅ Automated Deployment via GitLab CI/CD
✅ Infrastructure as Code with Terraform

Problems It Solves

  • Reliability: If one pod fails, another automatically takes over
  • Scalability: Add more replicas with a single configuration change
  • Visibility: Real-time monitoring of all systems
  • Automation: Zero-downtime deployments via GitOps
  • Consistency: Infrastructure as Code ensures reproducible setups
  • Easy Management: Declarative configuration instead of manual operations

3. Understanding Kubernetes

What is Kubernetes?

Kubernetes (K8s) is an orchestration platform for containerized applications. It automates deployment, scaling, and management of application containers across clusters of machines. Think of it as an intelligent container manager that keeps your applications running, scales them as needed, and handles failures automatically.

Key Kubernetes Concepts

📦 Pods

Definition: The smallest deployable unit in Kubernetes. A pod wraps one or more containers.

Key Points:
• Usually contains 1 container (rarely more)
• All containers in a pod share the same IP address
• Pods are ephemeral (temporary, can be created/destroyed)
• Example pod name: fastapi-app-78d65658cb-9zzwk
• Pod IP (internal): 10.42.0.114
• Pod gets unique hostname automatically

🎯 Services

Definition: An abstraction that defines a logical set of pods and a policy by which to access them. Services provide stable, load-balanced access to pods.

Why Services Matter:
Pods are temporary and get deleted/recreated. Services provide a stable endpoint that always works, even when underlying pods change. They also handle load balancing automatically.

Service Types:

  • ClusterIP: Internal-only access (default)
  • LoadBalancer: External IP + load balancing (what we use for FastAPI)
  • NodePort: Access via node IP + high port number
  • ExternalName: DNS alias to external service

🔄 Deployments

Definition: Manages the creation and updating of pod replicas. Ensures the desired number of pods are always running.

How Deployments Work:
1. You specify: "I want 3 copies of my app"
2. Deployment creates 3 pods automatically
3. If one pod fails, deployment creates a new one
4. When you update the image, deployment rolls out new pods gradually
5. Old pods are gracefully terminated = zero downtime!

🏷️ Namespaces

Definition: Virtual clusters within a Kubernetes cluster. Isolate different applications or environments.

Our Namespaces:

  • production: FastAPI application runs here
  • monitoring: Prometheus and Grafana run here
  • argocd: ArgoCD and deployment automation
  • kube-system: Core Kubernetes components

B. ArgoCD (GitOps Engine)

What it does:

ArgoCD watches your Git repository and automatically syncs any changes to your Kubernetes cluster. When you push code, ArgoCD detects it and deploys the new version automatically.

How it works:

  1. ArgoCD polls Git repository every 3 minutes (or on webhook)
  2. Compares current cluster state with Git desired state
  3. If different, applies the changes
  4. Uses Helm charts to render templates
  5. Applies rendered manifests to cluster
  6. Monitors rollout and reports health
Key Benefit: Your cluster state is always defined in Git. To change deployment, just modify Git - ArgoCD handles the rest!

Current Applications:

  • fastapi-prod: Production FastAPI deployment
  • prometheus: Metrics collection
  • grafana: Dashboards and alerting

Access:

ArgoCD UI: http://192.168.0.202

C. Prometheus (Metrics Collection)

What it does:

Prometheus collects time-series metrics from all applications and infrastructure components. It scrapes metrics, stores them, and provides query interface.

How it works:

  • Scrapes metrics from /metrics endpoints every 15 seconds
  • Stores metrics in time-series database
  • Default retention: 30 days
  • Provides query language (PromQL) for analysis
  • Can trigger alerts based on metric thresholds

Metrics Collected:

  • Application metrics: Request counts, latency, errors
  • Pod metrics: CPU usage, memory usage
  • Kubelet metrics: Node health, resource usage
  • Container metrics: Runtime stats

Access:

Prometheus UI: http://192.168.0.204:9090

E. MetalLB (Load Balancer)

What it does:

MetalLB implements LoadBalancer services in Kubernetes. It assigns external IPs from a configured pool to LoadBalancer services.

How it works:

  • IP Pool: 192.168.0.201 - 192.168.0.250
  • Protocol: Layer 2 (ARP-based)
  • Assignment: Automatic when service created
  • HA: 2 replicas for high availability
Why MetalLB Matters: Without it, LoadBalancer services would stay in "pending" state because Kubernetes doesn't have built-in external IP support. MetalLB fills this gap on bare metal/on-premise clusters.

F. Terraform (Infrastructure as Code)

What it does:

Terraform defines all infrastructure as code. Enables reproducible, version-controlled infrastructure.

What Terraform Manages:

5. Deployment Workflow

End-to-End Deployment Flow

Step 1: Developer Makes Code Change

# Edit application code vi src/main.py # Add new version field: "version": "v1.0.2"

Step 2: Commit and Push to Git

git add src/main.py git commit -m "Add version field to API response" git push origin master

Step 3: GitLab CI/CD Pipeline Runs

Build Stage:

  • GitLab CI runner executes pipeline
  • Dockerfile is read: build new Docker image
  • Image tagged with commit SHA and "latest"

Push Stage:

  • Docker image pushed to registry: 192.168.0.113:5000/fastapi-demo:latest
  • Image digest stored for reference

Deploy Stage:

  • CI runner connects to K8s cluster via SSH
  • Executes: kubectl rollout restart deployment/fastapi-app
  • Waits for deployment to complete
  • Displays status report

Step 4: Kubernetes Rolls Out New Pods

  • Deployment controller sees image change
  • Creates new pods with new image
  • Waits for new pods to be Ready
  • Gracefully terminates old pods
  • Redirects traffic gradually (rolling update)

Step 5: Changes Go Live

User refreshes browser at http://192.168.0.203/
New version is immediately returned!

Total time: ~30-60 seconds from push to live

Zero-Downtime Deployment Explanation

During deployment, Kubernetes uses a "rolling update" strategy:

  • maxSurge: 1 - Allow 1 extra pod during update (total 4 pods briefly)
  • maxUnavailable: 1 - Allow max 1 pod down during update (min 2 pods always running)
Timeline of Rolling Update: T=0s: [Pod1-old] [Pod2-old] [Pod3-old] ← Users hitting these T=5s: [Pod1-new] [Pod2-old] [Pod3-old] ← Pod1 restarted with new image T=10s: [Pod1-new] [Pod2-new] [Pod3-old] ← Pod2 restarted T=15s: [Pod1-new] [Pod2-new] [Pod3-new] ← Pod3 restarted T=20s: [Pod1-new] [Pod2-new] [Pod3-new] ← Deployment complete ⚠️ At NO point are all pods down = zero downtime!

7. Operations & Management

Common Operations

View Application Status

# Check deployment kubectl get deployment -n production # Check pods kubectl get pods -n production -o wide # Check services kubectl get svc -n production

View Logs

# View logs from a pod kubectl logs -n production # Follow logs in real-time kubectl logs -n production -f # View logs from all pods with label kubectl logs -n production -l app=fastapi-app -f

Scale Application

# Scale to 5 replicas kubectl scale deployment fastapi-app -n production --replicas=5 # Or edit deployment directly kubectl edit deployment fastapi-app -n production # Change replicas: 3 → 5, save and exit

Execute Command in Pod

# Run bash shell in pod kubectl exec -it -n production -- /bin/bash # Run single command kubectl exec -n production -- env | grep POD_IP

Restart Pods

# Restart all pods (rolling restart) kubectl rollout restart deployment/fastapi-app -n production # Wait for rollout to complete kubectl rollout status deployment/fastapi-app -n production

Monitoring and Troubleshooting

Common Issues and Solutions

Issue: Pod in CrashLoopBackOff state
Cause: Container crashes immediately after starting
Solution:
kubectl logs -n production
Check error message, fix application code or configuration
Issue: Pod stuck in Pending
Cause: Not enough resources or node unavailable
Solution:
kubectl describe pod -n production
Check resources and node status
Issue: Service not accessible externally
Cause: LoadBalancer IP not assigned
Solution:
kubectl get svc -n production
Check if EXTERNAL-IP is assigned, verify MetalLB running
